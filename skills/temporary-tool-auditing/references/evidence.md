# Evidence and limits

This recorder supports a bounded statement about one selected subject and one verified capture window. It does not establish universal proof that an agent never used a tool. The strongest supported absence statement is: no tool attempts were observed for the selected subject during the verified coverage interval.

Assessment requires a recorded positive control, verified hook activation, a completed subject inside the coverage interval, readable event and health logs, and no known coverage gaps. A positive control proves the recorder emitted an event in this run. It does not prove every runtime tool path is observable.

Pre-tool events represent observed attempts, including calls later rejected or failed. A post-tool event without independently structured outcome evidence has status `observed-unknown`; visible text alone is not treated as proof of success. Missing call IDs, duplicate events, unmatched pre/post events, malformed log lines, redactions, recorder health failures, and activity outside the selected attribution scope are surfaced as limitations.

Control calls are excluded only when their call ID, session ID, and agent ID match a control identity explicitly captured and registered in the manifest. A lifecycle-looking command is still a tool attempt when the selected subject issues it; command text alone never authorizes exclusion. Lifecycle commands must invoke the installed `auditctl.py` helper and pass this run's exact `--run-dir`; merely reading or mentioning the helper is ordinary tool activity. Assessment output returns the subject, detail level, covered intervals, coverage gaps, unresolved attempt count, health records, and redaction paths alongside the claim and its limitations.

Stopping or lease expiry may retain a post event that matches a previously recorded in-window attempt. Explicit disarm, removal, and verified teardown disable the recorder, including late-post writes. The audit control interpreter is persisted at installation and must still be available for teardown verification; a different current interpreter cannot stand in for it.

Codex child attribution uses the runtime's agent identifier when present. Main-session activity is selected by its session ID and the absence of a child agent ID; use an agent selector for a specific child. Devin hook events have session and prompt identifiers but do not expose a child agent identifier in the recorded harness evidence. Devin child attribution is therefore limited to captured, serialized dispatch boundaries, and the orchestrator and other agents must remain idle throughout that dispatch. `assess --confirm-parent-idle --apply` records the orchestrator's self-attested positional-attribution assumption; without it, child attribution is incomplete. Overlapping or unidentified activity makes the attribution ambiguous.

Evidence records are sanitized before persistence. Sanitization recognizes common credential field names and formats, authorization and cookie values, private-key blocks, URL user information and credential parameters, nested serialized JSON, JWTs, and selected personal/payment data such as email addresses, US Social Security numbers, and Luhn-valid payment card numbers. The broader class also includes health and government identifiers, bank data, source code, file paths, internal network names, and commercially sensitive information. Arbitrary names, confidential passages, locale-specific identifiers, and unknown secret formats cannot be recognized comprehensively by patterns. This is a defensive filter, not a secret detector or confidentiality guarantee. Choose only the detail the claim needs, never deliberately place credentials in a test call, and inspect the redaction report before using the evidence.

The recorder is observational and must not alter tool decisions. Remove only the exact owned project-local hook entries, restart the runtime when its configuration is cached, then run the teardown verification. A removed config entry alone does not prove that a running runtime unloaded its cached hook. After the assessment has established the bounded claim and teardown is verified, run `purge --apply` to remove event, health, and control logs and the known run-local recorder copies. Cleanup stays pending until purge is confirmed; unknown files are preserved and may require resolving before only the minimal sanitized cleanup receipt remains.
