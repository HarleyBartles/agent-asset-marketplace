# Codex hooks

Codex loads lifecycle hooks from active user, project, managed, and plugin configuration. This skill uses one stable user-wide dispatcher at `$CODEX_HOME/hooks.json` (normally `C:/Users/<user>/.codex/hooks.json`) and scripts under `$CODEX_HOME/tool-auditing/`. It preserves all unrelated hook entries. A changed, non-managed hook definition requires human review and trust before it runs. Install and approve the stable definition once. Restart Codex once only if the runtime needs it to load the new definition. Do not restart for engagement activation, pause, renewal, disablement, or purge.

The dispatcher covers `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop`, `SessionStart`, and `SessionEnd`. It reads the hook JSON from stdin. Before opening a run manifest or invoking the recorder, it requires a matching session ID, a matching worktree path, an active unexpired registry entry, and an armed manifest with the same run ID and project root. Missing or mismatched session/worktree information is inert and writes no audit event. Codex hook inputs include `session_id`, `cwd`, `hook_event_name`, `tool_name`, and `tool_input`; tool events carry `tool_use_id`. Subagent hook payloads use the parent session ID and may provide an `agent_id` for the child. A target session can therefore capture its own work and subagents while another session, even in the same worktree, remains excluded from the start.

The agent prepares from its own parent session while `CODEX_SESSION_ID` is available. The prepare helper persists this declared capture session ID as a narrowly whitelisted attribution field. Activation must match it. During the positive-control probe, verify the captured hook `session_id` equals the prepared value and that `cwd` resolves within the exact worktree. Do not substitute an app chat/thread ID or infer a missing session ID. The assessment subject can be a particular child agent inside the captured session family.

On Windows, the current-user environment variable `CODEX_TOOL_AUDIT_ACTIVATION_FILE` points to the session activation registry while one or more engagements are active. The dispatcher reads the current registry value from `HKCU\Environment` for every hook invocation; it does not trust the process's inherited environment copy. Enabling adds a run entry and sets the value. Disabling removes only that run entry and clears the value when no entries remain. A stale value with no matching entry is inert. On other platforms the dispatcher reads the registry file under `$CODEX_HOME/tool-auditing/` on each invocation. The file contains activation metadata only, not tool payloads.

Stop closes one observation round without uninstalling or disabling the engagement. The agent can assess/report, respond to a human request for follow-up, renew the lease, and start another interval with the same registration and run. Gaps caused by expiry remain gaps. When the engagement has fulfilled its purpose or is abandoned, disable that run. Verify that the activation entry is absent, the global definition still exists, the recorder health control succeeds, and a same-session runtime canary adds no event. Codex does not require a restart for this disablement check. Only then purge event, health, and control logs and run-local helper copies. Keep the stable dispatcher installed and inert between engagements.

The command has an absolute interpreter and dispatcher path with a Windows-specific command. It exits successfully with no output and never changes a tool decision. Hosted tools and specialized runtime paths outside demonstrated hook coverage remain explicit limitations. Consult the [official Hooks reference](https://learn.chatgpt.com/docs/hooks) when event fields or loading behavior changes.
