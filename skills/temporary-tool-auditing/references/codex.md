# Codex hooks

Codex loads hooks from active user and project configuration layers. Project hook configuration belongs in `<project>/.codex/hooks.json`; Codex merges matching hooks from active sources rather than replacing lower-level sources. It skips project hooks unless the project `.codex/` layer is trusted. A changed, non-managed hook definition requires human review and trust before it runs.

The installer previews and temporarily adds this exact project/worktree path to the active user `config.toml` as `projects."<absolute-path>".trust_level = "trusted"`. Review existing `.codex/` configuration and rules because trust makes that project layer eligible for loading. The installer never trusts a parent or wildcard path. If the exact path is explicitly `untrusted`, setup stops without overriding it. A pre-existing trusted entry is preserved. Teardown removes only the trust entry created by this run, preserves unrelated settings and user edits, and reports a conflict if the value changed. It compares the config snapshot immediately before replacement and stops if it detects an edit visible at that check; this does not serialize writers outside the helper's lock. The run journals its staging path before writing and resumes interrupted config replacement during retry or teardown. On Windows, it applies the existing config's DACL to the staged file and uses the file identity to recover documented partial replacement failures without creating a config backup. If identity recovery is unavailable or ambiguous, cleanup remains pending and the helper reports recovery paths. If a write reports recovery paths, resolve all reported files before continuing cleanup. `CODEX_HOME`, when set, determines the active user configuration directory.

The runtime reads hook definitions and trust settings at session start. After installation, inspect the exact worktree trust entry and have your human partner inspect and trust the generated handlers, then restart Codex before testing activation. The project trust entry makes its project-local configuration eligible for loading; it does not approve hook definitions. After removal, restart again and test a harmless tool canary before declaring teardown complete. The user's approval of an earlier hook definition does not automatically trust a changed definition.

The recorder listens to `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop`, `SessionStart`, and `SessionEnd`. Hook payloads include `session_id`, `hook_event_name`, `tool_name`, and `tool_input`; tool events carry `tool_use_id`. Subagent events can carry `agent_id`. Missing IDs remain missing. Main-thread tool events may not have an agent ID, so a session selector and an agent selector mean different scopes.

The handler command includes an absolute interpreter and recorder path, with a Windows-specific command for Windows Codex. The recorder exits successfully with no stdout so it does not return a decision or alter a tool call. Hosted tools are outside this local command-hook evidence boundary. The Codex documentation also cautions that specialized paths can opt out of the normal hook path, so describe coverage honestly.

Codex hook configuration, event contracts, trust, and tool coverage are described in the [official Hooks reference](https://learn.chatgpt.com/docs/hooks). Check it again when runtime behavior changes.
