# Operating contract

This reference preserves detailed operating guidance moved out of `SKILL.md` during progressive-discovery decomposition. Load it only when the compact control plane says the current task needs the full workflow.

# Adventures Frame Buster

Use this skill as the canonical router for what Harley calls frame buster: the whole pre-deck
framing family that must become green before deck planning, image planning, or PPTX production can
proceed.

This skill no longer owns every detailed framing test. It coordinates specialist busters, preserves
Harley's creative authority, and returns the combined readiness state.

This is deterministic no-credit work. It may inspect issues, partition source evidence, route framing checks, aggregate readiness, and name the next lawful downstream task. It must not generate or edit images, compile assets, build slides, post repo comments, mutate issues, or treat readiness as authority to spend image-generation credits.

## Source route discipline

Use bound `file_search` GitHub for broad repository discovery, stale-pattern sweeps,
and indexed corpus reads when it is available and relevant. Use live GitHub API
routes such as `api_tool` for exact issue, comment, file, commit, compare, and
authorized mutation operations.

If `file_search` is not bound and broad repo discovery would materially reduce
risk, ask Harley to bind the relevant GitHub connector before continuing, or state
that the pass is operating from narrower live API spot checks. Do not treat an
unbound `file_search` route as repo absence when another live GitHub route works.

## Core posture

Frame buster green means the framing family is green, not merely that a theme sounds good.

A candidate adventure is green only when the required checks collectively establish:

- a strong theme/world;
- a concrete real-world lesson;
- a Patch-led story spine;
- purposeful cast and interactions;
- grounded locations / domains;
- prop and state logic;
- asset preproduction order or asset-readiness handoff.

Do not privately invent or repair the frame when Harley must make a creative choice. Use interactive
buster posture for creation, selection, repair, or material extension. Use verification posture only
when the source issue/comments already contain a Harley-approved frame and you are checking whether
it is green as written.

## Task handoff map

Frame buster describes required framing tasks rather than naming dependent skills. When a specialist capability is
visible, GPT may discover it from the task vocabulary below. If no specialist is visible, perform the equivalent check
directly, mark the route as fallback, and do not claim a specialist was used.

Required framing tasks:

- world/theme viability;
- real-world teaching model, anti-pattern, positive pattern, and practical audience lesson;
- Patch agency, conflict, ordered progression, continuity object, and story state change;
- cast-to-real-world-function mapping and interaction purpose;
- location / command-domain mapping;
- props, tools-as-props, continuity objects, and state variants;
- final frame-readiness aggregation;
- visual preproduction order after frame green and before issue-to-PPTX production when assets are missing.

Do not encode a dependency on a particular skill name. Describe the next concrete task and let installed skill
discovery find the current capability that satisfies it.

## Readiness ladder

Use these states consistently:

- `seed_ready`: usable topic or adventure seed exists, but framing is thin.
- `theme_ready`: world/theme is viable but teaching/story/domain mapping may still be missing.
- `lesson_ready`: real-world anti-pattern and positive pattern are concrete and applicable.
- `story_ready`: Patch has agency, stakes, ordered progression, and a continuity/state transition.
- `frame_ready`: theme, lesson, story, cast, environment, and prop/state mapping are sufficiently green.
- `asset_order_ready`: frame is green and required visual preproduction outputs are listed.
- `asset_ready`: required pre-playbook asset sheets exist or have been accepted as sufficient.
- `playbook_ready`: frame_ready plus asset_ready. Only this should enter issue-to-PPTX production.

## Standard workflow

1. Inspect the source issue and comments when an issue number is available.
2. Extract existing frame signals: theme, world, real-world model, anti-pattern, positive pattern,
  Patch role, cast, locations, props, continuity object, ordered progression, asset decisions, and
  unresolved choices.
3. Decide whether this is verification posture or interactive creation/refinement posture.
4. Route through the specialist checks needed for the missing or risky areas.
5. Preserve partial statuses. Do not collapse theme_ready or story_ready into frame_ready.
6. If all framing checks are green, produce or request the visual preproduction order.
7. If asset readiness is missing, stop before playbook and route to visual preproduction.
8. If `playbook_ready` is achieved, state the next downstream task only. Do not begin issue ingestion, deck planning, image planning, PPTX building, repo comments, or image generation unless Harley's current turn separately asks for that specific downstream action.

## Image-credit and mutation boundary

Framing readiness is not visual-mutation authority. A green or playbook-ready frame, an asset-order list, a visual-risk note, a repair recommendation, or a user saying to continue the framing pass does not authorize image generation or generative editing. If downstream work may involve image tools, stop at a task handoff so visual-intent, image preflight, and image QA routes can enforce their own current-turn gates.

Use operation classes:

- `deterministic_no_credit`: issue inspection, source partitioning, framing checks, readiness aggregation, asset-order planning, route recommendation.
- `non_credit_pixel_work`: none owned by this skill; route deterministic asset/template work to the relevant compiler or contact-sheet workflow.
- `credit_spending_mutation`: not owned by this skill; never call image generation or generative editing from frame buster.

## Required output

For a normal framing pass, return:

- issue / source basis;
- posture: verification or interactive;
- current readiness state;
- theme status;
- lesson status;
- story status;
- cast/domain status;
- environment/domain status;
- prop/state status;
- asset order status;
- green / amber / red / blocked decision;
- exact blockers or Harley choices;
- next route.

## Stop conditions

Stop amber or red when:

- the lesson collapses to generic prompt advice or communication advice;
- Patch is decorative rather than active;
- the theme is interchangeable scenery;
- the cast does not map to real-world functions;
- locations do not represent command/work domains;
- props are ungrounded decoration;
- the continuity object/state transition is missing;
- asset preproduction would have to invent the visual world after framing;
- Harley must choose among real creative options.

## Patch and source discipline

Patch is singular. Do not create Patch clones or Patch-shaped helper agents. Supporting agents,
humans, systems, and audiences must be visually distinct from Patch.

For Patch visual work, downstream generation must start from repo-indexed Patch references and
matching project-source visual packages when needed. This router does not replace Adventures image
preflight or image QA task decisions.

## Operator-context quarantine

Treat bootstrap notes, session-buster-v0.2 continuity blocks, repo rollups, skill-installation lists, source-zip rebuild
reports, commit summaries, and next-session instructions as operator context. Use them to route and
verify work, but do
not turn them into issue content, story content, slide copy, image prompts, asset-sheet labels, or
audience-facing deck
material unless Harley explicitly asks for a status, continuity, or handoff artifact.

When a session-buster-v0.2 is present, extract the smallest task directive needed for this skill and quarantine the rest.
For visual work, the task directive should name the issue or frame, the artifact lane, scope, blockers, and required
verification. Operational metadata is not visual source material.

## Asset-discovery discipline

For asset-sensitive work, start at the first-level repo asset index, normally `assets/INDEX.md`. Use
the repo index mesh
to discover the current relevant asset families and source-package index. Do not hard-code second-level asset paths,
legacy package names, zip names, or a fixed count of style/reference files.

When package inspection is needed, locate the appropriate source zip or project-source package for
the task through the
index mesh, enumerate its own index or manifest, and consider every task-relevant file. Record skipped files with a
reason. First-level `assets` is a stable entry point; everything below it is discovered, not assumed.


## Frame-buster routing guard

Frame checks may decide that visual preproduction is needed, but they do not authorize image generation. If the
frame requires Patch-bearing visual proof, request a visual preproduction task for the Patch-in-world proof lane after
framing is green. Do not let bootstrap or buster text become part of the frame itself.
