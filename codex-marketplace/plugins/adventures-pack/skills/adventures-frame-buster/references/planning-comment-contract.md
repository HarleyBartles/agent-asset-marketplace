## Planning comment contract


When the frame becomes green and a source issue is available, land a GitHub issue comment before
deck planning proceeds. Use GitHub issue-management mechanics and Adventures repo issue
discipline.

The comment should include:

- frame name;
- thesis;
- why this frame fits the issue;
- analogy mapping from abstract terms to story objects/actions;
- actors and interactions, including Patch singularity and distinct supporting-agent roles;
- environment path;
- asset fit decisions: reused assets, assets explicitly not reused, and new provisional assets needed;
- adventure progression;
- conflict and cost;
- visual world and mood, with downstream Patch reference/source-package requirements when relevant;
- Patch's role;
- likely body-slide scene families;
- reusable asset candidates;
- analogy boundaries / risks;
- downstream planning instruction.

Keep the comment durable and concrete enough that another agent can plan the deck from it.
