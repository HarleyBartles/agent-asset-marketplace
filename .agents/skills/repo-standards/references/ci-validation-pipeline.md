# CI validation pipeline

Every repo that uses `repo-standards` should have a `tools/run.py` task runner
that composes the same checks CI runs for that repo.

- The `ci` task is the full non-mutating CI/PR verification gate. Use `ci --check`
  to prove the staged tree would pass hosted CI, and `ci --apply` to apply
  mechanical surfaces and validate them in fail-fast order.
- The `precommit` task is the tracked pre-commit hook's single complete local
  gate. `precommit --apply` applies mechanical surfaces, then runs every check
  and reports all independent failures instead of stopping at the first one.
- CI runs the same targets as separate workflow steps.

## Preflight: `tools/run.py precommit`

The `precommit` task is repo-owned and, in `--apply` mode, is the only complete
local gate a normal commit needs. It runs the same dependency order as `ci`:
`lint`, `repo-standards`, `validate`, and `archive-links`. In `precommit --apply`
it applies each mechanical surface, then runs every check and reports every
failure concisely so the next commit can succeed.

Run the smallest focused checks that prove the slice while iterating. For a
normal commit, stage the intended tree and let the tracked pre-commit hook run
`py -3 tools/run.py precommit --apply` as the single complete local gate.

## Pre-commit hook: `.git/hooks/pre-commit`

The hook is generated by `repo-standards` and executes
`py -3 tools/run.py precommit --apply` for every commit. If any step fails, the
commit is blocked and the failure report lists every target that must be fixed.
Do not bypass the hook with `--no-verify`.

## CI workflow

CI composes the same checks as separate workflow steps. Each step has its own
label so failures are easy to attribute. CI does not call the preflight script;
it runs the same commands directly.

## What to do when a check fails

A failing pre-commit run lists every failing target together with the repair
command. For example:

- lint -> `py -3 tools/run.py lint --apply`
- repo shape -> `py -3 tools/run.py repo-standards --apply`
- agent mesh -> `py -3 tools/run.py mesh --apply`
- marketplace drift -> `py -3 tools/run.py marketplace --apply`
- archive links -> `py -3 tools/run.py archive-links --apply`

Run the repair command for each failing target, then re-run only that target's
focused `--check` to confirm it is green before committing again:

- `py -3 tools/run.py lint --check`
- `py -3 tools/run.py repo-standards --check`
- `py -3 tools/run.py mesh --check`
- `py -3 tools/run.py marketplace --check`
- `py -3 tools/run.py archive-links --check`

Do not run the full `py -3 tools/run.py ci --check` immediately before a normal
commit or immediately after a successful hooked commit. The hook already proves
the staged tree.

## When to run the complete gate manually

Run the complete `py -3 tools/run.py ci --check` only in these cases:

- no normal commit will follow (for example, the final verification before flipping a PR to ready),
- you are diagnosing the pipeline and need a complete fail-fast report, or
- you are explicitly proving CI parity.

## Template menu

The `repo-standards` pre-commit template calls `py -3 tools/run.py precommit --apply`.
A repo can run the same tasks manually or wire them into CI:

- `py -3 tools/run.py precommit --apply` (pre-commit hook, reports all failures)
- `py -3 tools/run.py precommit --check` (diagnose without applying)
- `py -3 tools/run.py ci --check` (CI parity, fail-fast)
- `py -3 .agents/skills/repo-standards/scripts/repo_standards.py --check`
- `py -3 .agents/skills/repo-standards/scripts/scaffold-all.sh --check`
- `py -3 .agents/skills/generating-agent-mesh/scripts/validate_agent_mesh.py --check`
- `py -3 .agents/skills/refreshing-installed-skills/scripts/refresh_installed_skills.py --check`
- repo-specific lint command
- repo-specific final CI command
